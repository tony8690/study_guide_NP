Networking foundations & packet reasoning

An OCI Virtual Cloud Network (VCN) is regional and contains one or more non-overlapping IPv4 CIDR blocks, plus IPv6 prefixes when IPv6 is enabled. A subnet is a non-overlapping slice of that address space. It can be regional or availability-domain-specific; Oracle recommends regional subnets because they remove the subnet-level AD constraint and make it easier to design for an AD failure. Every subnet is also a configuration boundary: it has one route table, one set of DHCP options, and one or more security lists associated with it.

OCI reserves three IPv4 addresses in every subnet: the network address, the first host address used as the subnet default gateway, and the final address. In 192.168.0.0/24, those are 192.168.0.0, 192.168.0.1, and 192.168.0.255. CIDR planning must leave room for those reservations as well as growth, load balancer addresses, endpoints, and other service-created VNICs. Connected VCN and on-premises ranges must not overlap because OCI does not translate overlapping private address space for routing.

Public versus private subnet is an eligibility control, not a complete connectivity configuration. A private subnet prohibits public IPv4 addresses on its VNICs and prohibits internet communication for IPv6 endpoints. A public subnet permits them, but it does not automatically make an instance internet-reachable. IPv4 internet access still needs the appropriate public IP, an enabled Internet Gateway, a matching route, applicable security rules, and a permitting host firewall. For outbound-only IPv4 access from a resource without a public IP, route to a NAT Gateway instead.

A Compute instance receives a primary VNIC when it is launched; that VNIC cannot be removed. Every VNIC has a primary private IPv4 address from its subnet. Secondary VNICs can be added and removed, including in a different VCN, but all VNICs attached to one instance must be in the same availability domain as the instance. A VNIC can also hold secondary private IPs. Assigning or moving an address in OCI changes the control-plane object, but the guest operating system must also be able to use that VNIC or address, so an apparent OCI-side success does not prove the OS routing and interface configuration is correct.

Packet-path questions to answer

Use these as a study checklist rather than assuming that the presence of one resource proves connectivity:

  • What are the source and destination IPs, address family, protocol, and ports?
  • Which route table actually applies to the source IP or VNIC, and what is its longest matching route?
  • If traffic enters a DRG or gateway, which associated ingress route table makes the next decision?
  • Does the destination have a valid return route, especially through a stateful firewall or redundant hybrid path?
  • Do the subnet security lists, every attached NSG, any ZPR policy, any Network Firewall policy, and the host firewall permit the flow?
  • If the network path is valid, is the listener or application actually healthy on the expected port?

On-premises connectivity

The two primary on-premises paths are FastConnect and Site-to-Site IPSec VPN. FastConnect provides dedicated connectivity with predictable bandwidth; VPN runs over the public internet and is faster and cheaper to provision, so it is often the backup or the primary path for a smaller site. Native multicloud interconnects are a separate cloud-to-cloud category, not a third on-premises path, and Azure/GCP interconnects are not general-purpose transit services for an on-premises network.

FastConnect private peering, Site-to-Site VPN, and private multicloud interconnect paths reach VCN resources through a Dynamic Routing Gateway (DRG). FastConnect public peering is the exception: it reaches Oracle's public endpoints directly and does not use a DRG or VCN. Routed private paths require non-overlapping on-premises and OCI CIDRs. When you run two BGP paths for redundancy, AS-path length is a main preference lever: the shorter path wins, so you can prepend extra AS hops onto the backup path.

These private paths can converge on one DRG. FastConnect public peering is intentionally omitted because it goes directly to Oracle public endpoints without a DRG or VCN.

BGP & route selection

Border Gateway Protocol (BGP) exchanges reachable prefixes between autonomous systems. In OCI hybrid networking, FastConnect always uses BGP for route advertisement. A Site-to-Site VPN tunnel can instead use BGP dynamic routing, static routing, or the policy-based routing type. Establishing the BGP neighbor session is only the control-plane starting point: the relevant routes must also reach the correct DRG route table, and VCN route tables must send the corresponding traffic to the DRG.

Route selection starts with the destination prefix. A more-specific prefix wins before BGP path attributes are compared. When OCI has the same route through multiple hybrid paths, the course and Oracle routing documentation use AS_PATH to explain OCI's return-path decision: the shorter AS path is preferred. AS-path prepending on an advertised backup route makes that route less attractive to OCI. In the other direction, an on-premises router can use its own BGP policy—commonly a higher local preference on the chosen primary path—to decide how it sends traffic toward OCI.

For the same prefix and otherwise equivalent advertisement, Oracle's documented default preference is FastConnect first, then Site-to-Site VPN using BGP, then Site-to-Site VPN using static routing. Oracle represents those paths with resulting AS-path lengths of one, two, and three respectively. That default can be changed unintentionally if the customer adds enough prepends to a FastConnect advertisement, so the final advertised paths—not the service names alone—must be inspected.

OCI permits asymmetric routing: a request can enter through one connection and the reply can leave through another if route selection prefers that path. A stateful firewall in either direction may drop such traffic because it did not observe both halves of the session. Design active/backup paths with deliberate BGP policy and test failover in both directions. If equal-cost multipath is enabled on the relevant DRG route table, equivalent eligible routes can instead be active together and traffic is distributed per flow; ECMP is a routing design choice, not proof that the paths are physically redundant.

Original study scenario

On-premises advertises 192.0.2.0/24 over FastConnect and a BGP VPN. OCI sees the FastConnect path as length 1 and the VPN path as length 2. OCI therefore prefers FastConnect for traffic toward that prefix. If the on-premises router still sends OCI-bound traffic over the VPN, inspect the customer's outbound BGP policy—OCI's return-path preference does not configure the CPE's local preference.

FastConnect

FastConnect virtual circuits come in two flavors that are easy to mix up on the exam. A private peering virtual circuit reaches your actual VCN resources — it attaches to a DRG just like a VPN does. A public peering virtual circuit instead reaches Oracle's public services (Object Storage, public load balancer endpoints, and so on) over a dedicated connection instead of the public internet — useful when you want the reliability of a private link without exposing anything inside a VCN. Because public peering involves advertising your own public IP prefixes to Oracle, Oracle has to verify you actually own those prefixes before it will advertise OCI's public IPs back to you — a process that's documented as taking up to three business days, which is exactly the kind of detail exam questions like to test.

Physically, you can establish FastConnect three ways: by colocating your own equipment in an Oracle FastConnect location, through a FastConnect partner, or through a third-party provider network. For redundancy, cross-connects can be bundled into a Cross-Connect Group. BGP prefix limits differ by circuit type and are a favorite "why is BGP down" scenario: a private virtual circuit tops out at 2,000 IPv4 prefixes (500 for IPv6), while a public virtual circuit's limit is much lower at just 200 prefixes — advertise past either limit and OCI brings the BGP session down for 60 minutes, not just until you fix it.

Site-to-Site VPN

An OCI Site-to-Site VPN pairs a CPE object (representing your on-premises device) with an IPSec connection attached to a DRG. Each IPSec connection actually gives you two tunnels by default, terminating on different infrastructure, purely for redundancy — that's independent of whether you're also running a second VPN or FastConnect circuit for site-level redundancy. You can route over the tunnel statically (explicit CIDRs on both ends) or dynamically with BGP, and the choice usually comes down to whether your on-premises router supports BGP at all.

The most commonly tested quirk is what OCI's BGP implementation does to the AS path: it prepends its own ASN to routes it receives, so if you advertise a route with an AS path length of 1, OCI's side will see it as length 2. If you ever see that exact "+1" pattern in a scenario, it's telling you the connection is a BGP-based IPSec VPN — not FastConnect, not a static VPN.

Do not collapse all VPNs into simply “BGP or static.” In Site-to-Site VPN v2, BGP dynamic and static are route-based tunnel types: routing selects traffic for a virtual tunnel interface and OCI uses a single any/any encryption domain. The separate policy-based type matches explicit encryption domains, also called proxy IDs or traffic selectors, so the selectors configured in OCI must match the CPE. Multiple selectors sent to a route-based tunnel can produce unstable reachability; use the policy-based type when the CPE design genuinely depends on multiple encryption domains.

Static routes belong to the overall IPSec connection, not to one individual tunnel. A tunnel configured for static routing uses them, while a BGP tunnel ignores them. That connection-level behaviour matters when both redundant tunnels are available because OCI can use either route; the customer side must be designed for the resulting return path. BGP gives more direct control over active/backup preference, whereas a static design needs equally deliberate CPE route policy to avoid unintended asymmetry.

The cryptographic tunnel and its routing protocol have separate health signals. IPSec status UP confirms that the security association is established; for a dynamic tunnel, BGP status UP confirms the routing session. Neither alone proves that the wanted prefix is installed through the correct DRG route table or that VCN routing and security permit the application flow. Oracle supports IKEv1 and IKEv2, configured per tunnel. When changing IKE version, routing type, or a shared secret, change and validate one redundant tunnel at a time. If the CPE is behind NAT, configure the CPE IKE identifier that Oracle should expect.

A specialized variant, IPsec over FastConnect, exists for when you want the low, predictable latency of a dedicated circuit but still need encryption in transit (private peering FastConnect alone is not encrypted). Create a CPE object with IPsec over FastConnect enabled, then create the IPSec connection and map its tunnels to enabled FastConnect virtual circuits. OCI uses an Oracle-managed LOOPBACK attachment internally to connect the virtual-circuit and IPSec-tunnel attachments; the CPE object itself is not the loopback attachment. Because each tunnel individually caps out well below a full circuit's bandwidth, OCI supports ECMP across up to 8 tunnels on one connection so you can scale total encrypted throughput up to what the underlying FastConnect circuit can deliver.

Remote peering & transit routing

Local Peering Gateways work within one region. Across regions, a Remote Peering Connection (RPC) connects the regional DRGs over Oracle's backbone without using the public internet. OCI protects inter-region traffic between Oracle data centres, including MACsec encryption on the backbone. RPC can connect only regions in the same OCI Realm; every region belongs to exactly one realm.

The concept that trips people up most is transit routing: getting traffic to flow all the way from on-premises, through one region's DRG, across an RPC, into a second region's DRG, and finally into that region's VCN — and back again. This doesn't happen automatically just because the physical/logical connections exist. Dynamically advertised attachment routes enter a DRG route table according to its assigned import route distribution; static route rules can also be added directly. For two-way dynamic transit you need distributions configured in both directions: import the on-premises-facing attachment's routes into the RPC's DRG route table, and import the RPC attachment's routes into the on-premises-facing attachment's DRG route table — and mirror that same pair of distributions on the DRG in the second region.

Multicloud interconnects

Oracle Interconnect for Microsoft Azure supports split-cloud workloads over private, low-latency connectivity in specific paired regions. A DRG/FastConnect virtual circuit on OCI connects to Azure ExpressRoute. Latency still varies with the selected region pair and topology; Oracle does not document one universal sub-2-ms guarantee. The setup begins in Azure by creating ExpressRoute and obtaining its service key, which is then used to create the OCI virtual circuit.

Oracle Interconnect for Google Cloud pairs an OCI DRG/FastConnect connection with Google Cloud Router and Partner Cross-Cloud Interconnect. Its documented setup begins in Google Cloud by creating VLAN attachments and pairing keys, then uses those keys in OCI.

Oracle Interconnect for AWS is the newest of the three (limited availability at launch) and breaks the pattern in one meaningful way: it's the only one of the three that can be initiated from either side — you can start the request from the OCI console or from AWS's Direct Connect console (look for "AWS Interconnect (multicloud)" there). Whichever side starts it, the other side has to accept and exchange a service key before BGP comes up; the finished connection reports independently on each console (OCI shows the virtual circuit as Provisioned with BGP up, AWS shows the connection as Available), with built-in IPv4 and IPv6 BGP redundancy validated on both ends. A common but non-ideal fallback some designs still reach for is standing up VPN software on a VM to tunnel from OCI to AWS — Oracle's best-practice guidance is explicit that whenever a native interconnect service is available, using it beats building and maintaining your own VM-based tunnel.

Azure and Google workflows begin in the partner cloud and continue in OCI with exchanged keys. The AWS workflow can begin from either console.

Dynamic routing gateway

The DRG is the piece that ties everything together: VCN, IPSec VPN, FastConnect private virtual circuit, and RPC attachments connect to it. Attaching two resources does not by itself guarantee mutual routing; the ingress attachment's associated DRG route table and that table's import route distribution decide the egress path. A new DRG has two default route tables: the table used by VCN attachments imports routes from all attachments, while the table used by IPSec, virtual-circuit and RPC attachments imports VCN routes only. The defaults therefore are not a full mesh between every non-VCN attachment.

For hub-and-spoke isolation, associate each spoke attachment with a DRG route table whose import distribution excludes other spoke attachments while importing the hub. Dynamically advertised attachment routes enter a DRG route table according to its assigned import route distribution, which can be autogenerated or custom. You can also add static route rules directly to a DRG route table.

A DRG route table entry can also show a Conflict status when two IPSec tunnel or virtual-circuit attachments advertise equivalent routes. With ECMP disabled, OCI makes an arbitrary but stable choice among otherwise identical routes of the same source type; do not design around "first learned" being guaranteed. Enabling ECMP tells OCI to treat equal-cost routes as active and load-share across them.

The packet-walk rule is simple but easy to miss: a DRG route lookup happens when traffic enters through an attachment, using the DRG route table associated with that ingress attachment. The selected rule names the next-hop attachment. Import distributions decide which advertised routes are inserted into a table; export distributions describe which routes are advertised from a table to an attachment. These policies populate or advertise routes—they do not replace the VCN route that first sends traffic to the DRG.

Original study scenario

VCN A and VCN B are attached to the same DRG. VCN A reaches on-premises but VCN B does not. “Both are attached” is not enough: verify VCN B's route to the DRG, the DRG route table associated with the VCN B attachment, its imported on-premises prefix and next-hop tunnel or virtual circuit, and the on-premises return route for VCN B.

Virtual cloud network design

A VCN is a set of CIDR blocks plus the plumbing you attach to it: subnets, route tables, and security rules. Subnets are regional by default, spanning every availability domain in the region. Traffic between subnets in the same VCN uses implicit local routing; security lists and NSGs still gate it. OCI lets you add, remove, resize, or replace IPv4 CIDR blocks with safeguards: the resulting ranges must preserve every in-use address and fully contain existing subnet CIDRs, and routes/security references may also need updating.

Two features worth knowing cold for the exam: VCN Flow Logs capture traffic metadata (source, destination, ports, accept/reject) for auditing and troubleshooting without capturing payload, and OCI supports dual-stack IPv4/IPv6 VCNs. For IPv6 subnetting math, remember the rule of thumb — going from a /56 VCN allocation to /64 subnets uses 8 bits, so 2^8 = 256 possible subnets, and that pattern scales the same way for any GUA-to-subnet size difference.

Every instance connects through a VNIC (Virtual Network Interface Card), which always gets a private IP from its subnet's CIDR; a VNIC in a public subnet can additionally be assigned a public IP. DHCP Options is a small but real VCN-level resource attached to each subnet — since OCI runs DHCP for you, the only things you actually configure are the DNS type (the built-in Internet and VCN Resolver, or a custom DNS server IP you specify) and the DNS search domain instances should use.

Every VNIC gets a private IP from its subnet's CIDR regardless of type — only a public subnet's VNICs are eligible for a public IP on top of that.

VCN route tables & packet paths

A VCN route rule has two essential fields: a destination and a target, or next hop. Targets include a DRG, Internet Gateway, NAT Gateway, Service Gateway, LPG, or a private IP used by an appliance. OCI chooses the most-specific matching destination—the longest prefix match. A route for 10.20.30.0/24 therefore wins over 10.20.0.0/16 for an address inside both ranges. If no route matches traffic that must leave the local network, OCI drops it; creating a gateway does not create every required route automatically.

OCI supplies implicit local routes between subnets in the same VCN. They are not shown as ordinary user rules. Current VCN routing also supports explicit intra-VCN static routes through a DRG, LPG, or private-IP next hop. For the same prefix, a user-defined static route has priority over the implicit local route, which is how east/west traffic can be forced through a firewall. Traffic whose destination is in the same subnet is forwarded directly rather than routed, so intra-subnet inspection cannot be created simply by adding a subnet route rule.

The subnet route table is no longer always the effective table. OCI supports per-resource routing on a VNIC or on an individual primary or secondary IP. Selection is hierarchical: an IP-level route table takes priority over a VNIC-level table, which takes priority over the subnet table. Only one table is used for that lookup; OCI does not fall through to the VNIC or subnet table when the selected IP-level table lacks a route. This is a strong troubleshooting clue when two workloads in the same subnet follow different paths.

Traffic leaving a subnet normally uses the effective IP, VNIC, or subnet route table. Traffic entering a VCN through a supported gateway can instead use a gateway-associated ingress route table. Oracle supports these associations on LPGs, DRGs, Internet Gateways, NAT Gateways, and Service Gateways. Ingress routing makes designs such as “internet → IGW → firewall private IP → application subnet” possible. It also means a topology diagram showing the gateway is incomplete unless you know which route table is attached to it.

When a private IP is the route target, its VNIC must be allowed to forward traffic: enable skip source/destination check and configure IP forwarding in the appliance operating system. A secondary private IP can be moved between VNICs in the same subnet to give the route target a recoverable identity, but that does not remove the need for equivalent appliance configuration and symmetric return routes.

Route-table hierarchy selects one table. Longest-prefix match is then evaluated inside that selected table.

Two VNICs share one subnet. The subnet table has 0.0.0.0/0 → NAT Gateway, but VNIC B has its own route table containing only 10.50.0.0/16 → DRG. IP address management

OCI gives you more control over addressing than "just pick a CIDR," and the exam draws a sharp line between the ephemeral and reserved lifecycle for both public and private IPs. An Ephemeral Public IP is tied to the VNIC that requested it — exactly one per VNIC, and it's released permanently the moment that VNIC or instance terminates; you cannot convert it into something persistent after the fact. A Reserved Public IP, by contrast, is its own standalone resource with an independent lifecycle: you can create it before you need it, attach it to an instance, detach it, and reattach it to a completely different instance later — the address survives instance termination. The identical pattern exists on the private side with Reserved Private IPs, which is how you build a "floating IP" that fails over between two instances in an HA pair.

A tenant-created Public IP Pool contains BYOIP IPv4 CIDR blocks you have brought to OCI; Oracle-supplied addresses come from the built-in Oracle source pool rather than a custom pool you assemble. Reserved Public IPs can be allocated from the appropriate source pool. Separately, a VNIC can be assigned secondary private IPs from the subnet's address space, a pattern used for failover addresses, containers, or multiple logical services behind one VNIC.

An IP CIDR address assigned to a VNIC represents a contiguous range of host addresses as one secondary IP object rather than creating every address separately in OCI. The range still comes from an eligible subnet prefix and must not overlap addresses already in use or reserved by OCI. This is useful when a workload—such as a container or network appliance—needs many addresses behind one VNIC. The guest operating system still needs the corresponding interface, routes, or application bindings; assigning the CIDR object in the Console alone does not configure the software consuming every address.

IP Address Insights provides a tenancy-wide, hierarchical inventory across compartments, VCNs, subnets, and network resources. It shows used addresses and CIDR utilisation, identifies address conflicts, and supports utilisation alarms. Use it for planning and exhaustion detection rather than treating it as a live packet-troubleshooting tool: Oracle documents that utilisation data is collected and published periodically, so brief changes may not appear immediately.

IPv6 architecture

OCI VCNs are always built with IPv4 and can optionally operate as dual stack. Enabling IPv6 at the VCN does not automatically enable it on every subnet or VNIC: the VCN must have a prefix, each participating subnet must be IPv6-enabled, and each participating VNIC or supported service must receive an IPv6 address. A VCN can therefore mix IPv4-only subnets with dual-stack subnets.

There are three prefix sources to distinguish. Oracle can allocate a /56 Global Unicast Address (GUA) prefix. You can bring a qualifying BYOIPv6 GUA prefix, or assign a Unique Local Address (ULA) prefix for private communication. Every IPv6-enabled subnet is /64. An Oracle-assigned or BYO GUA can be internet-routable only when the resource is in a public subnet and the routing and security configuration permit it. A ULA is not advertised to or routed through the internet even if its subnet is public.

IPv6 does not use the IPv4 pattern of attaching a separate public address object to a private address. The subnet's public/private flag controls whether GUA endpoints may communicate with the internet. A GUA in a private subnet remains prohibited from internet communication. OCI supports IPv6 through an Internet Gateway, LPG, and DRG; NAT Gateway and Service Gateway are not IPv6 route targets. For internet routing, use an IPv6 rule such as ::/0 → Internet Gateway rather than sending IPv6 to a NAT Gateway.

IPv4 and IPv6 routes can coexist in the same VCN route table, but the rules are separate: an IPv4 default route does not match IPv6. Security rules are separate too. An IPv4 SSH or ICMP rule does not allow the IPv6 equivalent. ICMPv6 is operationally important; for example, the default IPv6 security rules include Packet Too Big messages used by Path MTU Discovery. When enabling IPv6 for FastConnect or VPN, configure the hybrid connection for IPv6 and add both the IPv6 VCN route and the appropriate IPv6 security rules.

The Flexible Load Balancer can be created dual stack, receiving client traffic on IPv4 or IPv6 while using IPv4 to reach its backends. Oracle documents that IPv6 assignment for this service is selected at load-balancer creation rather than added later. Treat the frontend and backend address families separately when a scenario asks whether an IPv6 client requires IPv6 application servers.

Original study scenario

A VNIC has a GUA, but it is in a private subnet. Adding ::/0 → Internet Gateway does not make it internet-reachable because the private-subnet flag prohibits IPv6 internet communication. The correct conclusion is not “missing NAT”; IPv6 through a NAT Gateway is not the supported model.

DNS: public, private & traffic steering

OCI Public DNS is authoritative for zones you delegate to it, with answers served from Oracle's anycast edge. In Private DNS, each VCN has its own dedicated resolver at 169.254.169.254. A private view can be attached to multiple resolvers and contains private zones. Resolver rules—not view rules—send matching domains through a forwarding endpoint to an external or on-premises DNS server. A separate listening endpoint accepts queries entering OCI from the hybrid network.

Private resolution has an explicit evaluation order: attached views in their configured order, then the protected default view if it was not already included, then ordered resolver rules, then internet resolution. A matching private zone can end evaluation even with an authoritative negative response such as NXDOMAIN, unless a suitable private-zone transparency mode is configured. This is why a broader private zone can unexpectedly prevent a forwarding rule from being reached.

Resolver rules are also first-match. Once a rule condition matches, its forwarding action runs and later rules are not evaluated—even if that destination is unavailable. Two duplicate forwarding rules therefore do not provide DNS-server failover. Oracle's documented pattern is a single forwarding rule aimed at an NLB with redundant DNS backends; the course also demonstrates the NLB DNS health check for removing an unhealthy DNS backend.

Traffic Management steering policies let a single DNS record return different answers depending on who's asking or what's healthy, evaluated against configurable health checks: load balancer/ratio policies split traffic by weighted percentage (the mechanism behind gradual, DNS-based migrations); failover policies return a backup answer only when the primary is unhealthy; geolocation and ASN policies answer based on the query's geographic origin or originating network; and IP-prefix policies key off the querying resolver's CIDR block.

DNSSEC is supported for public zones. OCI creates and manages the zone's DNSSEC keys and replacement KSKs/ZSKs; during a KSK rollover, the customer updates the parent zone's DS record and then promotes the new KSK in OCI. Signed responses use records including DNSKEY, RRSIG, DS, and NSEC3. Private zones do not support DNSSEC. When migrating a signed public zone, coordinate the source and delegation carefully so the parent DS record never points at an unavailable key.

Internet & NAT gateways

An Internet Gateway (IGW) lets resources with an assigned public IP send and receive internet traffic when routing and security allow it. At Oracle's edge, OCI maps the VNIC's private IP to its assigned public IP and reverses that mapping for replies; this is different from a NAT Gateway's shared, stateful outbound translation. A NAT Gateway lets private resources with no public IP initiate internet connections while preventing unsolicited inbound initiation. A subnet route table can mix targets because OCI evaluates the most specific matching route rule.

An IGW existing in the VCN is only one prerequisite. For direct IPv4 internet access, the gateway must be enabled, the subnet must be public, the relevant private IP must have a public IP association, the effective route table must send the internet destination to the IGW, the applicable security rules must permit the traffic, and the host firewall or application must accept it. A failure in any one produces the same user symptom, so “the IGW is attached” is not a complete diagnosis.

A NAT Gateway does not require an Internet Gateway. It owns the public-side translation used for connections initiated by eligible private resources. Configure the private workload's effective route—commonly 0.0.0.0/0 → NAT Gateway—plus egress security and DNS as required. A NAT Gateway is not a path for an internet client to initiate a new session to the private instance, and it is not a generic internet transit gateway for traffic arriving from an on-premises network or peered VCN.

Service gateway, private endpoints & PSA

A Service Gateway lets private clients reach supported regional Oracle services without using the public internet. One gateway serves the VCN via route rules that target an Oracle Services Network service CIDR label; the services still use Oracle public service IP ranges, but traffic stays on Oracle's network. Connections must be client initiated: an Oracle service cannot initiate a new connection through the gateway. The client can be inside the VCN or on-premises when ingress routing is deliberately configured from a DRG attachment through a transit VCN to the Service Gateway, with a return route from the Service Gateway to the DRG.

A Private Endpoint takes a different, per-resource approach: it gives one specific service resource — a single Autonomous Database, or Object Storage scoped to particular buckets, namespaces, or compartments — its own dedicated private IP and FQDN inside a subnet you choose. It's granular but not shared: provision five Autonomous Databases with private access and you get five separate private endpoints, each with its own address. Some services also build on this for a Reverse Connection Endpoint (RCE) — a narrower capability that lets a supported Oracle service initiate a secure connection back into your network, the one case where traffic flows in the opposite direction from a Service Gateway.

Private Service Access (PSA) is a third, separate resource type — not just an umbrella term covering the other two. A PSA endpoint is its own VNIC with one dedicated private IP and FQDN per service API, shared across every resource of that type: a single PSA endpoint covers all five of those Autonomous Databases, the way a Service Gateway covers a whole region's services, but addressed with a private IP instead of a shared public CIDR label. It supports IPv4-only or dual-stack IPv4/IPv6 networks, and access is controlled exactly like any other VNIC — security lists, NSGs, or Zero Trust Packet Routing policies. For Object Storage specifically, a PSA endpoint blocks cross-tenancy pre-authenticated requests, foreign-tenancy credentials, and anonymous access, and supports up to 25 Gbps of throughput — which is why Oracle recommends PSA as the default choice for most private Object Storage designs, reserving Private Endpoint for cases that need to restrict access to specific buckets, namespaces, or compartments for particular clients.

A standard Private Endpoint is client-initiated access to one service resource. A Reverse Connection Endpoint is a separate, service-specific construct for supported service-initiated flows. Service Gateway uses a regional public service CIDR label; Private Endpoint and PSA use private addresses.

Local peering gateway

An LPG peers exactly two VCNs, and only within the same region — that's the entire scope of what it does, which is also why it's such a clean contrast with RPC on the exam (same region → LPG, cross region → RPC). A VCN can have multiple LPGs to peer with multiple partner VCNs, each pair needing non-overlapping CIDRs. In hub-and-spoke designs built with LPGs rather than a DRG, the hub's LPG for each spoke can carry its own VCN route table, which is what actually determines how traffic arriving from that spoke gets routed once it's inside the hub.

Inter-tenancy connectivity & IAM

VCNs in different tenancies can be connected with different constructs depending on topology. Two same-region VCNs can use cross-tenancy LPG peering. A VCN can also attach to a DRG owned by another tenancy in the same region, which is useful when one tenancy owns a shared routing hub. For cross-region connectivity, each side uses a DRG and Remote Peering Connection (RPC). The chosen construct changes the required IAM resource types, so there is no single generic policy block that should be copied into every cross-tenancy design.

Same-tenancy attachments use normal OCI permissions. Cross-tenancy networking additionally requires explicit agreement from both tenancies. The administrators exchange the required tenancy, group, compartment, and network-resource OCIDs and create complementary policies. IAM authorises who may establish or manage the relationship; it does not create packet routes or security rules.

Three policy statement types form the cross-tenancy handshake. Define assigns a local alias to a remote tenancy, group, compartment, or resource OCID. Endorse belongs in the source/requestor tenancy and states what its group may do in another tenancy. Admit belongs in the destination/acceptor tenancy and grants the corresponding external group permission in that tenancy. Endorse and Admit must correspond; either statement by itself grants no cross-tenancy access. For a cross-region design, both tenancies must also be subscribed to the required regions.

The requestor is the side that initiates the LPG or RPC connection after the policies exist; the other side is the acceptor. Connected or Peered status proves that the control-plane relationship was established. Data-plane connectivity still requires non-overlapping CIDRs, a route on both VCN sides, the correct DRG route table and import distribution where a DRG is used, applicable security rules on both endpoints, and a working return path.

IAM establishes authority to connect. It is separate from the routing and security configuration that carries application traffic.

Security lists & NSGs

Both security lists and network security groups (NSGs) are firewall rule sets, and OCI evaluates them together rather than one overriding the other — a packet is allowed through if any applicable rule, from either mechanism, permits it. The difference is scope: a security list's rules apply to every VNIC in the subnet it's attached to, while an NSG's rules apply only to the specific VNICs you've explicitly added to that NSG, regardless of which subnet they live in. That makes NSGs the better tool for microsegmentation — you can define a "web-tier" NSG and a "db-tier" NSG, write a rule that says "allow traffic from the web-tier NSG to the db-tier NSG" (referencing the NSG itself as the source, not a CIDR), and that rule keeps working correctly even as you add or move instances between subnets. Both mechanisms support stateful rules (return traffic auto-allowed) or stateless rules (both directions must be explicit). One limit worth remembering: an NSG-as-source reference only works within a single VCN — cross-VCN, the only native option is a CIDR-based rule, which is exactly the gap Cross-VCN ZPR (below) is designed to close.

A complete security rule identifies its direction, whether it is stateful or stateless, source or destination type, IP protocol, and—where applicable—source port, destination port, or ICMP type and code. For an ingress TCP rule, the destination port is normally the service being protected, such as 22 or 443; the client source port is commonly an ephemeral port and should not be confused with the server's listening port. IPv4 and IPv6 CIDRs require separate rules.

A stateful rule tracks the connection and automatically permits response traffic. A stateless rule does not, so the return direction needs its own applicable rule. If the same traffic matches both a stateful and stateless rule in one direction, Oracle documents that the stateless rule takes precedence and the connection is not tracked. This is why adding a broad stateless rule can break a flow that previously relied on stateful return handling.

The effective OCI packet-rule set is the union of the subnet's security lists and every NSG attached to the VNIC: any matching rule in that union can allow the packet. ZPR is different—an attributed endpoint must also satisfy its ZPR policy. Compute platform images also have an operating-system firewall. A correct NSG rule does not override a closed firewalld, iptables, or Windows Firewall rule, and an open host firewall does not override a missing OCI rule.

NSG membership is normally managed from the parent resource. For a Compute instance, you edit the relevant VNIC; for a Load Balancer or database service, you edit that resource. The rule still applies to the service-managed VNIC. An NSG starts empty and has no default rules, so attaching a newly created NSG does not itself open traffic.

Zero Trust Packet Routing

OCI Zero Trust Packet Routing (ZPR) is a different kind of security control from security lists, NSGs, or a firewall: instead of IP/CIDR/port rules tied to the network layout, you write intent-based policies in near-English, like "in the prod VCN, allow compute instances tagged app:science to connect to the database tagged database:sensitive on port 1521." The mechanics are two steps. First, you tag resources with security attributes — a namespace plus an attribute name and value, e.g. network:carconet for a VCN or app:tele-app for a compute instance. Second, you write a ZPR policy referencing those attributes; the policy is enforced at the packet layer, independent of whatever the route tables and security lists say.

The detail that matters most for the exam: the instant you attach a ZPR attribute to a resource, that resource flips to deny-by-default for ZPR purposes — even if a security list or NSG already permits the traffic, it's blocked until an explicit ZPR policy opens it. All three layers (security list/NSG, network firewall, ZPR) are then evaluated as a logical AND: a packet needs every applicable layer's blessing to get through, not just one. This is precisely how ZPR defends against the classic "someone tweaked a route table while fixing an unrelated issue and accidentally exposed the database to the internet" scenario — since ZPR doesn't care what the route table says, the database stays protected regardless.

Cross-VCN ZPR extends the same attribute model across VCN boundaries. In a hub-and-spoke design with a shared Network Firewall in the hub, NSGs and security lists still enforce port-level control at the edge, and the firewall still does SSL inspection, intrusion prevention, and URL filtering — but neither of those stops one application's load balancer in the hub from reaching a completely different application's compute instance in another spoke, because NSG references don't cross VCNs and CIDR-based cross-VCN rules are brittle. Tagging each app's resources with distinct attribute values and writing narrow Cross-VCN ZPR policies between only the matching pairs closes that lateral-movement gap without touching a single route table.

Network firewall & inline NVAs

For inline inspection, a third-party firewall or OCI Network Firewall is placed in the routed data path. OCI Network Firewall is a managed service; Oracle operates the firewall infrastructure while you define the inspection policy and the routes that steer traffic through it. A central hub can inspect several VCNs, while a distributed design places a firewall closer to each workload. The right choice depends on routing, isolation, failure-domain, and scale requirements.

Firewall resource, policy, and rule components

The firewall resource is the endpoint created in a VCN subnet. The firewall policy is a separate resource selected by the firewall and contains reusable address, application, service, and URL lists plus security rules. TLS inspection adds mapped secrets, decryption profiles, and decryption rules. Create the policy before the firewall; an attached policy with no security rules denies all traffic.

Security rules match configured source and destination address lists, applications, services, and URL lists, and are evaluated in their configured order. Actions include allow, silent drop, reject with a reset, intrusion detection, and intrusion prevention. URL lists support Oracle's documented wildcard forms; examining URL path or query data in encrypted HTTPS requires decryption. This is deeper inspection than a VCN security rule, but it does not replace NSGs or security lists.

The packet must reach the firewall—and return through it

Subnet or NSG rules are evaluated before traffic reaches Network Firewall, so they must allow the intended flow for the firewall policy to inspect it. Route both directions deliberately: steer the forward path to the firewall IP, provide the firewall subnet with its next hop, and steer return traffic back through the firewall when stateful inspection requires symmetry. Internet, on-premises, and east/west patterns use different route-table associations; drawing only the forward arrow is not enough.

Tunnel Inspection pairs OCI Network Firewall with a VTAP: the VTAP mirrors clear-text traffic inside a VXLAN encapsulation to the firewall out-of-band, where the tunnel is decapsulated and the inner traffic is inspected. This is separate from TLS decryption rules and does not block the original production flow. A tunnel-inspection rule can use Inspect or Inspect and capture log; tunnel-session logging therefore depends on the selected action and logging configuration.

Web application firewall

OCI Web Application Firewall is a Layer 7 control for HTTP(S). For a current deployment, create a regional WAF Policy, then create a WAF firewall resource that associates that policy with an OCI Flexible Load Balancer HTTP listener. The older global WAF Edge Policy is a legacy WAAS service. WAF cannot protect a Network Load Balancer.

WAF's rule conditions are written in JMESPath, a query language that evaluates a JSON document describing the request or response — for example, a condition checking whether the request's country code equals a blocked value. Each rule pairs a condition with an action: Allow, Check (logs the match but doesn't stop rule processing, useful for tuning before enforcing), or Return HTTP Response (blocks the request or response and substitutes a custom reply). Beyond access control, WAF bundles rate limiting (per-IP request throttling against Layer 7 DDoS), bot management (JavaScript challenges, human-interaction checks, CAPTCHA, device fingerprinting, and a good-bot allowlist), protection rules against SQL injection/XSS/HTML injection sourced from OWASP guidance, and caching rules at the edge for eligible content. A Network Address List (NAL) is a separate, reusable object holding a set of trusted IPs/CIDRs — reference one in a rule to allowlist or blocklist a group of addresses (e.g. trusted partner ranges) without hand-writing a JMESPath condition per address. When the goal is specifically distinguishing bots from real users on a form like registration or checkout, CAPTCHA is the purpose-built tool — rate limiting caps volume regardless of who's asking, and a NAL only helps if you already know which addresses to trust or block.

Load balancer & NLB

OCI has two different load-balancing services. The Flexible Load Balancer is a terminating reverse proxy for TCP and HTTP-family workloads. Its HTTP, HTTPS, HTTP/2, and gRPC listeners can provide Layer 7 features such as TLS termination, header inspection, session persistence, and host- or path-based routing. The Network Load Balancer (NLB) makes connection-level decisions from Layer 3/4 information and is designed for very high throughput and low latency. It supports TCP, UDP, and other IP traffic, but it does not terminate TLS or inspect HTTP content.

Know the object relationship

A listener is the front door: it defines the protocol, port, and—for a Flexible Load Balancer—optional TLS configuration. A listener sends traffic to a backend set. The backend set combines three things that are often tested separately: a list of backend servers, a load-balancing policy, and a health-check policy. Flexible Load Balancer policies include round robin, least connections, and IP hash. SSL configuration and session persistence can also be configured for a backend set.

For HTTP or HTTPS, a routing policy is an ordered list attached to a listener. Each request is evaluated from the first rule downward; the first matching condition routes it to the named backend set and stops evaluation. A request that matches no rule goes to the listener's default backend set. This is request routing, not the same thing as a VCN route table.

NLB modes are not interchangeable

  • Full NAT: the NLB translates both source and destination before forwarding to a backend.
  • Source preservation: the NLB preserves the client source IP and port but performs destination NAT from the listener VIP to the backend.
  • Transparent source/destination preservation: the NLB changes neither side of the packet. This private-NLB-only mode is used as a route-table next hop for “bump-in-the-wire” appliances such as NVAs.

NLB distribution policies hash a 5-tuple, 3-tuple, or 2-tuple. The default 5-tuple policy keeps packets in one TCP or UDP flow on the same backend; the 3- and 2-tuple choices provide affinity beyond a single transport session. Choose a mode and policy from the packet behavior the application or appliance requires—do not assume every NLB preserves both headers.

Reachability and health are separate checks

Load Balancer and NLB backends can be outside the balancer's own VCN when those addresses are reachable through the VCN's routing, including a peered VCN, another region, or on-premises. Route tables, NSGs, security lists, and return routing must still permit the flow. Flexible Load Balancer health checks can test TCP or HTTP; NLB health checks can test TCP, UDP, or HTTP. HTTP checks can validate a URI, status code, and response body. After the configured health-check retry or failure threshold marks a backend unhealthy, it is normally removed from rotation until it passes again; an NLB backend set can instead be configured to fail open and continue using its current distribution if every backend is unhealthy.

Certificates & TLS

In a TLS handshake, the server presents an end-entity (leaf) certificate and the client validates its identity, validity period, signature, and chain to a root that the client already trusts. A chain commonly runs leaf → subordinate CA → root CA. A private root created or imported in OCI is not automatically trusted by browsers or operating systems; the root or appropriate CA bundle must be placed in each relying client's trust store. In mutual TLS (mTLS), the server also requests and validates a client certificate, so both sides authenticate with certificates.

OCI Certificates manages three different concerns: certificate authorities, certificates, and CA bundles. An OCI private CA can issue subordinate CAs and leaf certificates; creating an internally managed CA requires an HSM-protected asymmetric key in OCI Vault. A CA bundle contains one or more CA certificates used to establish a chain of trust. A third-party certificate can also be imported, but importing it requires the leaf certificate, its certificate chain, and the matching private key in supported PEM formats. These models are not interchangeable: an internally issued and internally managed certificate lets the service manage its private key and can use automated renewal; an internally issued but externally managed certificate is created from your CSR while you retain its private key; and an imported certificate was issued outside OCI and is updated by supplying replacement PEM content.

Renewal creates a new certificate version. OCI can automate renewal only for certificates that it both issued and manages; imported certificates and certificates whose private keys are managed externally require a manual PEM or CSR update. Revocation invalidates a version before expiry, but the Certificates service can revoke only resources issued by an internal CA—not imported or externally managed certificates—and CRL publishing requires a configured Object Storage bucket. To delete a certificate, first remove all associations. Deletion is then scheduled; the default permanent-deletion date is 30 days later, with a minimum delay of one day.

Bastion

OCI Bastion removes the need for a self-managed jump host by brokering short-lived SSH or RDP sessions into private resources. Managed SSH needs OpenSSH, Oracle Cloud Agent and the Bastion plugin on the target. SSH/RDP port forwarding targets one host/port without the agent, while dynamic port forwarding can reach multiple hosts in the target subnet. Bastion accepts supported OpenSSH public keys such as RSA and Ed25519; Ed25519 is not an exclusive requirement. For RSA keys with newer OpenSSH clients, compatibility settings may be needed. Sessions last 30–180 minutes.

The mechanic worth internalizing is where traffic actually comes from once a session is active: the target resource sees the connection arriving from Bastion's own private endpoint IP, not from the original client's IP address. That means the target's security list or NSG should be scoped to allow the relevant port from that endpoint IP — opening the port to your entire corporate CIDR instead would defeat the purpose of routing through Bastion at all. Sessions also aren't permanent; each one lasts a minimum of 30 minutes up to a maximum time-to-live of 3 hours (180 minutes), after which it expires and you create a new one. Cloud Shell Private Network Access is a different mechanism: it must attach to a subnet in the home region, although that subnet can use peering routes to other regions.

Cloud Shell

Cloud Shell is not a resource you create in your VCN. It is a browser-based Linux terminal embedded in the OCI Console, with a pre-authenticated OCI CLI and tools such as Ansible and Python. Its API permissions come from your existing IAM policies; opening Cloud Shell grants no extra tenancy access. The session VM runs Oracle Linux 8, but root access and sudo are unavailable, so do not infer that you can install any OS package simply by naming a package manager. Many user-space tools can instead be unpacked into the persistent 5-GB home directory.

Oracle documents three networking modes. OCI Service Network is the default and reaches OCI-wide services for your tenancy in the home region without public-internet access. Cloud Shell Public Network provides public-internet access only when an administrator grants the required IAM permission and no Security Zone policy forbids it. Private Network Access attaches the session to a selected private subnet; it can be saved as a private-network definition or created as a temporary ephemeral private network for one session.

The VCN and subnet selected for Private Network Access must be in the tenancy's home region, but routes from that subnet can reach a peered VCN in another region. Cloud Shell still behaves like a private instance for routing and security, and custom-DNS resolver endpoints are not supported for this feature. The ping command is not allowed in Cloud Shell, so use configuration tools such as Path Analyzer or run ICMP tests from a suitable Compute instance.

VTAP

A Virtual Test Access Point mirrors a copy of traffic to a chosen destination without changing the original flow's route—useful for security monitoring, deep troubleshooting, or compliance capture. Configuring one comes down to three pieces: a capture filter defining which traffic qualifies; a source naming the monitored resource, such as a Compute VNIC, Load Balancer, DB system, Exadata VM Cluster, or Autonomous AI Lakehouse private endpoint; and a target that receives the copy.

The current target type is an OCI Network Load Balancer in the same VCN as the source, although it can be in a different subnet or compartment. Mirrored traffic is VXLAN encapsulated; Oracle's reference architecture recommends an NLB UDP listener on port 4789. Capture-filter include/exclude rules are ordered and first-match. You can set a maximum mirrored packet size from 64 to 9,000 bytes, including truncating it for more efficient ingestion.

Mirroring consumes source bandwidth. Production traffic has priority by default; priority mode gives monitored and mirrored traffic equal priority, so congestion can cause some monitored traffic to be dropped—it does not guarantee delivery of every mirrored copy. A VTAP is created in STOPPED state and must be started before it mirrors traffic.

VCN flow logs

VCN Flow Logs answer a narrower question than VTAP: “what connection metadata did this VNIC observe, and did its effective VCN security accept or reject it?” Each record represents one direction of traffic for one VNIC and includes source/destination IP, source/destination port, protocol, packets/bytes, and ACCEPT or REJECT disposition—never packet payload. Records cover one-minute capture windows and are delivered through OCI Logging for search, export, or streaming.

Flow Logs and VTAP use separate capture-filter types with similar ordered include/exclude rules; a Flow Log filter also has a sampling rate. Current enablement-point types are a whole VCN, a subnet, or Resources. In the Resources picker, the exact current choices are Instance VNIC, Network load balancer, or one or more VNIC OCIDs. Use the narrowest scope and filter that still answers the question.

A REJECT record means a security list or NSG rejected that directional flow. It does not identify the single rule to change, and it is not proof of a routing failure. Conversely, ACCEPT means the VNIC's effective security allowed that direction; it does not prove the route, remote return path, host firewall, or application worked. Correlate both directions and all applicable security lists and NSGs.

Know the evidence gaps: some link-local Oracle service traffic and ARP are excluded; traffic to a Compute public IP is recorded against the corresponding private IP; and NODATA or SKIPDATA indicates no captured traffic or omitted data for that window. Use VTAP when packet content is required.

Console workflow

Navigation menu → Networking → Network Command Center → Flow logs → Enable flow logs

  1. Select or create the destination log group.
  2. Create a Flow Log capture filter with ordered direction, CIDR or IPv6 prefix, protocol/port, include/exclude, and sampling settings. ACCEPT/REJECT is recorded output, not a filter criterion.
  3. Add a Virtual cloud network, Subnet, or Resources enablement point; then make the specific selection inside that type.
  4. Generate the real traffic, then open the resulting log in OCI Logging and correlate source, destination, direction, time, and disposition.

Network Command Center tools

Network Visualizer renders deployed topology from live configuration. Inter-Region Latency shows rolling five-minute average round-trip time, refreshed every minute, between region pairs in the current OCI realm (except a realm with only one region). Use it for planning and broad baseline visibility; Oracle explicitly says it is not intended for workload troubleshooting.

Network Path Analyzer goes a step further than visualization: give it a source and destination (OCI-to-OCI, on-premises-to-OCI, or OCI-to-internet) and it performs a non-intrusive, simulated hop-by-hop reachability check—no real traffic is generated—and can display as many as 8 possible paths. It reports the routing and security configuration evaluated at each hop, which can expose a missing route or allow rule even before test traffic exists.

Its caveats matter. Same-subnet endpoints with different private IPs can produce incorrect results; cross-tenancy LPGs and cross-tenancy or cross-region RPCs can return Indeterminate; IPv6 and routing loops are unsupported; and current intra-VCN or Internet Gateway routing can make results inaccurate. A simulated “reachable” result also does not prove that the guest OS, application, or on-premises device is healthy.

Systematic OCI network troubleshooting

The course tools become much easier to use when the packet walk comes first. Treat the following as an Oracle-source-based study workflow, not a claim that the exam always follows this order.

1. Define one exact flow

Write down source IP, destination IP, protocol, source and destination ports, and who initiates the connection. Record whether the addresses are private, public, IPv4, or IPv6. Resolve a DNS name separately so that a name-resolution failure is not mistaken for a routing failure.

2. Walk the forward route

At the source VNIC, identify the effective IP-, VNIC-, or subnet-level route table and apply longest-prefix match. Confirm the selected next hop exists and is enabled. At every gateway, inspect its associated ingress route table where applicable. When traffic enters a DRG, use the route table associated with the ingress attachment and confirm its import distribution supplied the expected route.

3. Walk the return route independently

Repeat the lookup from the destination toward the source. Check remote VCN tables, DRG associations, BGP advertisements, VPN tunnel choices, and on-premises routing. An Up IPSec or BGP status does not prove that the application prefixes or a symmetric return path exist.

4. Check every enforcement layer

Evaluate the union of the subnet security lists and every NSG attached to the relevant VNIC, then consider stateless behavior and reply rules. Where used, evaluate Zero Trust Packet Routing as a separate required allow, Network Firewall policy and routing, and finally the operating-system firewall. Routing chooses a path; none of these controls creates that path.

5. Validate the service endpoint

For a load balancer, separate listener reachability from backend-set health. For DNS, inspect the resolver view, ordered forwarding rules, endpoint reachability, and the authoritative answer. For hybrid links, compare IPSec, BGP, FastConnect, and DRG status with the actual prefixes learned and advertised. Test the application locally on the backend where possible.

6. Choose evidence that answers the question

  • Network Visualizer: understand the deployed topology, route-table relationships, and security associations. It is a map, not a packet generator.
  • Network Path Analyzer: simulate configuration-based reachability without sending packets. Use its reported status together with its documented unsupported cases.
  • VCN Flow Logs: inspect metadata from traffic that actually occurred. Each record represents one direction and shows addresses, ports, protocol, volume, and ACCEPT/REJECT disposition. A REJECT narrows the problem to effective security rules, but the record does not name the single rule to edit.
  • VTAP: mirror packet copies from a supported source through VXLAN to a same-VCN NLB and packet-analysis backend. Use it when headers or payload behavior—not just connection metadata—must be inspected; a newly created VTAP is stopped until started.
  • Metrics and service logs: verify real resource state and performance. OCI publishes namespaces for VNICs, DRGs, FastConnect, Internet/NAT/Service Gateways, VPN, Load Balancer, NLB, and Network Firewall.

Original study scenario

Path Analyzer reports a configured route and security path to a web server, but the TCP connection still fails. Do not rewrite the route table solely because the simulation is reachable. Generate a real connection, inspect Flow Logs, confirm the instance firewall and listening socket, and use VTAP only if packet-level evidence is needed. Path Analyzer models OCI configuration; it does not start the application.

Workload migration

Moving workloads into OCI touches three separate problems: getting the data there, keeping IP dependencies intact, and cutting DNS over safely. For bulk data migration into Object Storage, OCI documents four paths: over the plain internet via HTTPS; over a FastConnect public-peering circuit, which reaches Oracle's public services over a dedicated line instead of the internet without ever touching a VCN's DRG; over FastConnect private peering, where the DRG's VCN route table sends Object-Storage-bound traffic to a Service Gateway (the DRG attachment alone doesn't reach the Oracle Services Network — you still need that Service Gateway route); or physically, via the Data Transfer Appliance, for one-time transfers at the petabyte scale where even a fast circuit would take too long.

Bring Your Own IP (BYOIP) solves the "hard-coded IP address" problem that trips up a lot of migrations: instead of re-numbering everything that points at your current public IPs, you delegate your own owned public CIDR to Oracle, which then advertises that exact range from OCI's edge — external consumers keep working against the same addresses, unaware anything moved, and OCI's IP-pool management helps preserve the range's reputation. Finally, DNS-based cutover uses a ratio-based (weighted) load balancing Traffic Management steering policy to shift a percentage of live traffic — say, 10% — from the existing on-premises deployment to a freshly stood-up OCI copy, then dials that percentage up as confidence grows, all without an all-or-nothing switch. As with any hybrid connectivity project, none of this works if the on-premises and OCI CIDR ranges overlap — that non-overlap requirement is a prerequisite before FastConnect or VPN can even be configured.

Networking best practices

Oracle's own best-practices guidance groups into four areas, and the exam draws individual facts from each. On design: do the networking design work early, before deployment, because some decisions are painful or impossible to reverse later — the standout example is that a private subnet can never have a public IP added to it, so guessing wrong on public-vs-private means rebuilding the subnet. Standardize naming conventions, choose subnet type and regional-vs-AD-specific scope deliberately, size CIDRs for future growth rather than just today's needs, and build custom route tables and security lists instead of leaving everything on the VCN's auto-generated defaults. A hub-and-spoke design is explicitly called out as the pattern to reach for once you need shared services, centralized security inspection, or isolation between multiple VCNs.

On security: Oracle recommends network security groups over security lists as the default choice, precisely because a security list's rules apply to every VNIC in the subnet — as a subnet grows, that quietly widens access far beyond what any individual workload needs, whereas an NSG only ever applies to the VNICs you explicitly add to it. Use the free managed OCI Bastion service instead of standing up and patching your own jump host, restrict who can touch networking resources with scoped IAM policies, and add OCI Network Firewall (or a third-party equivalent) where you need application-aware inspection beyond the CIDR, protocol, and port controls provided by security lists and NSGs.

On connectivity: build full redundancy for any hybrid link, which specifically means validating that two FastConnect circuits terminate on physically different routers, not just that you have "two circuits." Prefer FastConnect over VPN as your primary path (FastConnect's dedicated bandwidth and predictable performance beat the public internet every time cost isn't the deciding factor), keep VPN as the backup path or as the primary only when cost sensitivity rules FastConnect out, test failover on a regular cadence, and lean on custom DRG route tables and import route distributions — including on any transit-routing design — rather than the defaults.

On monitoring, observability, and management: use the Network Command Center tools proactively rather than treating them as interchangeable incident tools. Visualizer shows implemented topology, Path Analyzer evaluates configured reachability without sending test packets, and Inter-Region Latency provides regional planning statistics rather than workload troubleshooting. Set up event notifications on critical networking resources so configuration changes and outages surface promptly rather than being discovered through a user complaint.
